# Annexe : critique de complétude du plan POLY (brut, en anglais)

```
CRITIQUE OF "JAMRACK POLY — plan final"
(checked against the research blocks, the three judges, and the repo at /home/user/jamrack; numbers marked "computed" were recomputed here)

(a) FACTUAL / PHYSICS ERRORS STILL PRESENT
- quote: "B(corde) ajusté par moindres carrés sur les partiels 2-12 (Barbancho 2012)" and "partiels inharmoniques f_n = n·f0·√(1+B·n²)".
  error: inharmonicity is not a per-string constant. B ∝ 1/L², so fretting multiplies B by (f_fret/f_open)² = 2^(fret/6): fret 12 has 4× the open-string B (computed), fret 19 ≈ 9×. Barbancho 2012 itself models β(s,n) per string AND fret. With one B per string the synthesised 20th partial at fret 12 lands ~1 bin off.
  correction: B(string,fret) = B_open(string)·2^(fret/6); the quick calibration at frets 0/5/12 gives three points per string to fit B_open and verify the scaling.
- quote: "Décalage de ±1 bin piloté par l'accordeur si une corde est > 15 cents à côté".
  error: a detune scales every partial proportionally; at 11.7 Hz/bin (24 kHz, FFT 2048), 15 cents is 0.06 bin on E2's fundamental but 2.5 bins on the 10th partial of E4. A uniform ±1-bin shift corrects at most one partial and mis-aligns the rest.
  correction: regenerate the template from the parametric model with f0·2^(cents/1200), or resample the template along frequency by that ratio.
- quote: "off quand < pic − RELEASE dB pendant 24 ms ... Note-off attendu 40-60 ms après étouffement sur les graves".
  error: this only holds for the exponential variant of the window. For the "montée courte, plateau jusqu'au présent" variant of the MEDIUM window, 24 ms of silence lowers the windowed partial energy by only 4.8 dB and 36 ms by 16.6 dB (computed, 1024 samples @ 24 kHz); any RELEASE ≥ 15 dB plus the 24 ms hold gives ~60-70 ms. With an exponential window τ = 8-12 ms a 20 dB drop shows after 18-28 ms (computed), so the 40-60 ms claim is reachable.
  correction: pick the exponential window for voice-level/note-off tracking (and say so); keep the plateau window, if at all, only for the NMF note-on spectrum. Also add the resulting resolution loss to the plan: an exponential window of τ = 10 ms has a main lobe far wider than a 43 ms Hann, so it cannot be the note-on spectrum for the low strings.
- quote: "Rack + attaque synthé | 0-2,7 | prochain quantum".
  error: the note-on leaves the audio thread (worklet port.postMessage, js/input/guitar.js:121), is handled on the main thread (routeNoteOn) and re-enters the graph via AudioParam scheduling at ctx.currentTime, which is already ≥ 1 quantum ahead. That is ≥ 2 quanta (5.3 ms) plus main-thread event-loop jitter (UI redraw, meter updates), typically 3-10 ms, not 0-2.7 ms. The instrument's own attack envelope is not counted either.
  correction: budget 5-10 ms for this hop, and add it to the measurement list (it is invisible to the current IN/OUT/TRK readout, rack.js:296, which only reports ctx latencies and the tracker's internal latMs).
- quote: "WASM SIMD ≈ 0,45-0,6 ms (17-22 %, FFT et NMF 5-23× plus rapides, mesuré)".
  error: the 5×/23× figures were measured for a 144×1024 matvec on the worklet thread; no wasm FFT was benchmarked anywhere in the research (the only FFT number is 0.115 ms in JS, Node). The YIN kernel gained only 1.9× in wasm (no SIMD gain).
  correction: "matvec/NMF 5-23× measured; FFT and YIN gains unmeasured (YIN 1.9× in Node)".
- quote: "POLY JS v1 ≈ 1,3-1,6 ms (50-60 %, A/B bureau seulement)".
  error: this is an average, but the gate the plan itself defines is p99, and the p99 happens inside an attack window where the plan runs SHORT + MEDIUM FFTs every hop, LONG every 2 hops, NMF on ≥ 2 spectra and a residual YIN pass. Using the research's own numbers (FFT 0.115 ms Node ×2.5 worklet ≈ 0.29 ms; NMF 0.18 ×2.5 ≈ 0.45 ms; YIN diff 0.42 ×2.5 ≈ 1.05 ms; front end + flux ≈ 0.1 ms) a burst hop costs ≈ 2.3-3.0 ms, i.e. at or above the 2.67 ms quantum. Judge 3 flagged the YIN cost; the plan did not absorb it.
  correction: state the burst-hop cost separately, cap the residual YIN to the SHORT window (n=512) or to every second hop during bursts, and make jalon 7 (WASM) conditional on the burst p99, not the mean.
- quote: "Détection d'attaque | 3-5 | flux HF, Kehling 2014 F=0,95 à 5 ms".
  error: Kehling's F = 0.95 is for the rectified-complex-domain detector on 5 ms frames; frequency-weighted spectral flux scored 0.93 at 8 ms frames, and both are accuracy figures, not latencies.
  correction: cite it as "accuracy 0.93-0.95 at 5-8 ms frames"; the 3-5 ms latency remains an assumption to measure on plucks.mjs.
- quote: "Note seule, pincement → note-on | 9-36 ms | inchangé (chemin rapide)".
  error: the fast path is gated on "aucune voix ne sonne"; a lead note played over a still-ringing chord (10 % of solo onsets in GuitarSet land on a ringing string, jamrack research) takes the NMF path (15-40 ms).
  correction: "unchanged only when nothing else is ringing; otherwise POLY latency applies".
- quote: "une seule note par corde (sinon off+on)".
  error: string assignment from a mono pickup is only ~82 % correct offline (Kehling 2014, SVM on inharmonicity features), and same-pitch positions on adjacent strings (e.g. E4 on B-5 vs high-E-0) differ only by B, which the generic bank cannot resolve. A hard "one per string" rule will cut a real ringing note whenever the string guess is wrong.
  correction: apply the rule as "one note per pitch class per string group" or only when the two candidates' string posteriors are both > ~0.8; otherwise fall back to "one note per pitch".
- quote (section 1) "Environ 10-12 sessions d'agents pour une bêta POLY crédible" vs the milestone table: jalons 1-6 sum to 13.5 sessions (14.5 with the reserve), 15.5-16.5 if jalon 7 fires.
  correction: 13-16 sessions, or drop something.
- quote (jalon 4) "p99 ≤ 60 % JS bureau" vs section 4 "Porte = p99 ... ≤ 30 % bureau, ≤ 20-25 % iPhone" vs jalon 7 trigger "si p99 > 25-30 %" and criterion "p99 ≤ 25 % bureau". Four different thresholds for one gate.
  correction: one table: JS v1 may ship on desktop at p99 ≤ 40 %; WASM triggered above that; WASM must land ≤ 25 % desktop / ≤ 20 % iPhone; iPhone POLY off until then.

(b) IMPORTANT THINGS MISSING
- No stated channel for the user's recordings to reach the agent. 25 min of 48 kHz/24-bit mono ≈ 216 MB; gh-pages is one-way. The plan must name the transfer path (GitHub release asset on the user's repo, Drive link, or a page-side recorder that produces a downloadable WAV the user attaches to an issue) or jalon 6 cannot start.
- "Relevés IN / OUT / TRK ... plus CPU affiché pendant une note tenue" is asked for before jalons 1-3, but the CPU readout is only delivered in jalon 4 ("lecture CPU/TRK"). Either ship the readout as a 0.2-session pre-step or drop CPU from item 2.
- No acceptance criteria for bend lag, note-off latency, velocity, or "note avant le pincement" although section 4 asserts numbers for all of them (bend 15-25 ms, off 40-60 ms). Add to jalon 3: bend lag p50 ≤ 25 ms on plucks.mjs with bend; per-string off ≤ 45 ms (high) / ≤ 70 ms (low) after cut; 0 note-ons before the pluck sample; per-voice velocity within ±15 % of the single-note velocity for the same pluck level inside a chord.
- The GuitarSet baselines are on different take sets (mono F 0.724 on 24 solo / 12 comp takes; Basic Pitch 0.791 / 0.732 on 6 + 6 takes). The reference table in jalon 1 must rescore both on the committed fixed list.
- Firefox is never mentioned (AudioWorklet since 76, SIMD since 89, and JS speed on its worklet thread unmeasured). Add one Playwright Firefox render to the CPU gate; also Playwright ships WebKit (JavaScriptCore) on Linux, which would give the only iOS-engine proxy available here for JS-vs-wasm SIMD throughput before the user's iPhone readout. Not verified installed (~/.cache/ms-playwright is empty); `npx playwright install webkit firefox` is a cheap first task.
- Window-shape dependency not stated: the template bank is "une version par longueur de fenêtre" but templates must also be built with the same asymmetric window shape as the analysis, otherwise the W/V mismatch the plan just fixed for length reappears for shape (an exponential or ramp+plateau window has very different main-lobe/sidelobe structure from Hann). Say "per length AND per shape", and record the shape in the profile.
- Pickup-position comb filtering in the quick calibration: synthesising frets 1-19 from 0/5/12 by shifting the inharmonic pattern ignores that the pickup notch sits at a fixed distance from the bridge, so it moves across partial numbers with fret. The plan should state that quick-calibrated banks are expected to lose a few points and that jalon 5 measures FULL vs QUICK on the user's chords.
- Cost of item 7's hex pickup is understated: "micro hexaphonique (~170 $)" needs a 6-input interface (not in the user's known rig; ~200-500 $) and 13-pin wiring; the research says so.
- "GPU loué (≈ 10-30 $/run)" has no provenance, and the plan does not say who rents it: the agent cannot provision one and the user does not code, so jalon 9 is in practice blocked unless the user creates an account and the agent is handed credentials; state it.
- No rollback/exposure plan: POLY should ship behind the card toggle defaulting to MONO, with `state.guitar.mode` persisted and the gh-pages test deployment on a separate branch so users of the main page never see a regression.
- Missing dependency for the latency table: the current IN/OUT numbers in the card rely on ctx.outputLatency/baseLatency (guitar.js:203-204) and engine.js already uses latencyHint 0 on desktop; Chrome on Windows may report outputLatency = 0, in which case the readout the plan asks the user for will understate OUT. Ask for a loopback measurement (click → mic) rather than the displayed number, or ship the "--loopback-test" idea in the page itself.
- Safari and ws://127.0.0.1: the plan lists it as unverified for Chrome, but WebKit has historically not applied the localhost mixed-content exemption; if the helper (jalon 8) targets macOS the WebSocket transport may need wss with a self-signed cert or MIDI (midir virtual port) instead. Add to "non vérifié".
- No listening check-list content for item 6; define it now (10 items: single notes per string, dyads, open chords slow/fast, barré, arpeggio, mute inside chord, bend on one string, hammer-on inside chord, fast repick, 30 s free play), each scored usable/unusable.

(c) ITEMS IN "CE QUE VOUS DEVEZ FOURNIR" THAT ARE UNNECESSARY OR REPLACEABLE
- "âge des cordes" (item 1): irrelevant to any decision in the plan; the calibration date and a 1-minute recalibration already cover it. Drop.
- "Windows 10/11 (24H2+ ?)" (item 1): only matters for Windows MIDI Services loopback in the optional helper, and the plan already prefers the WebSocket transport. Move to jalon 8.
- Item 3's chromatic part ("chaque corde chromatique du vide à la case 19") duplicates item 4 ("calibration complète : 120 pincements") — the in-app recorder of jalon 5 captures exactly this. Keep one: have the user record the chromatic set once, through the page, when jalon 5 exists; before that, prototype the template bank on public DI data: IDMT-SMT-Guitar subset 1 (Zenodo 7544110, three electric guitars, every string/fret, CC BY-NC-ND, evaluation/development only, nothing redistributed) is exactly the chromatic set, and GuitarSet hex-stem remixes give exactly-labelled chords. Items 3 and 4 then become "20 doubles-notes + accords + jeu libre" (≈ 12 min) plus the in-app calibration.
- Item 5(c) (rust/ folder decision) and 5(d) (GPLv3 helper, 99 $/an) are decisions for conditional jalons 7-8; asking for them now adds noise. Only 5(a) (per-guitar calibration) and 5(b) (note-off behaviour) gate jalons 3-6.
- Item 2's iPhone/Safari readouts can be deferred: the plan already defaults iPhone to MONO and gates POLY on a WASM build; Chrome/PC readouts are the ones that gate jalons 4-6.
- Item 7 "essai MIDI Guitar 2 / bêta MG3 dans Reaper": the GuitarSet part of this protocol needs no user action beyond installing the plugin; the plan could instead ask only for the DAW-rendered MIDI files of 6 fixed takes (the WAVs and scoring script come from the repo).
```
